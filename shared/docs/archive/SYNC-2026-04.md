### Q6. Empty `usage: {}` in SSE `done` event

`docs/CLUSTER-USAGE-TRACKING.md` documents that the gateway's
per-user token accounting records zero today because the cluster
emits an empty `usage` object. Backend plans to fix this soon.
Before we do: what exactly does the gateway read? We want to match
the shape precisely so we don't cause another silent regression.

Confirm the gateway's `stream_and_log()` still reads the shape
described in that doc (i.e.,
`{"prompt_tokens": N, "completion_tokens": N}`). If you've moved
to a different shape (e.g. OpenAI's nested `usage.usage.*`),
tell us so we can emit accordingly.

**Frontend answer:**

> The gateway reads from **any SSE `data:` line that contains `"usage"`**. Parsing logic (identical in both `/api/` and `/v1/` proxy paths):
>
> ```python
> usage = data.get("usage", {})
> tokens_total = usage.get("total_tokens", 0) or (
>     usage.get("prompt_tokens", 0) + usage.get("completion_tokens", 0)
> )
> ```
>
> So it accepts either shape:
> - `{"usage": {"total_tokens": N}}`, preferred, single field
> - `{"usage": {"prompt_tokens": N, "completion_tokens": N}}`, fallback, summed
>
> The `usage` object must be a top-level key in the SSE data JSON. It does NOT need to be in a specifically-typed event, the gateway scans every `data:` line. Emit in the `done` event for simplicity.
>
> **Current status:** All historical API key usage entries show 0 tokens because the cluster emits `usage: {}`. Browser chat via `/api/chat/completions` correctly reports tokens (the cluster fills usage for persona-mode SSE?). This is the single highest-priority fix for accurate billing.

### Q7. Conversation-level default tags (§28 follow-up)

Planned backend work: add `default_tags` column to `conversations`
so `#tag` chips the user pinned on turn 1 stick through the rest
of the conversation without the frontend re-submitting on every
turn. Before we commit to the API:

- Do you currently re-submit `tags` every turn? (This is the
  current contract.)
- If we add the column, would you rather the frontend SET the
  default explicitly (`PATCH /api/chats/{id}` with
  `default_tags`) or have the backend auto-persist the first
  request's tags as the default?

**Frontend answer:**

> - **Yes, the frontend re-submits `tags` on every turn.** `activeTags` is React state in `App.tsx` that persists across messages and is included in every `sendMessage()` call. Tags are never auto-cleared.
> - **Preference: backend auto-persists the first request's tags as the default.** This is simpler, no extra PATCH call needed. The frontend can continue sending `tags` on every turn (harmless), and the backend uses the conversation's `default_tags` as a fallback when the frontend omits `tags` (e.g., when resuming an old conversation).
> - **Edge case to handle:** If the user changes tags mid-conversation (removes one, adds another), the frontend will send the updated `tags` array. The backend should use the explicitly-sent `tags` when present, falling back to `default_tags` only when `tags` is absent/empty.
>
> **Backend follow-up (2026-04-21, shipped):** implemented exactly as specified.
>
> - New `default_tags` column on `conversations` (JSON-serialised `list[{kind, value}]`, NULL = no default).
> - On new-conversation creation, the first request's normalised tags are persisted as `default_tags`. `normalized_tags` is None → NULL stored.
> - Per-turn resolution in `_resolve_effective_tags(body_tags, default_tags)`: body tags (this turn) override; missing body tags fall back to `default_tags`; neither → None (unscoped). Pure function, unit-tested.
> - Never merges, per your edge case, an explicit body `tags` removes the implicit default for that turn. If the user wants to re-pin, they send tags again.
> - Ephemeral conversations skip the fallback entirely (no persistence layer; body tags are the only signal).
> - No new endpoint, the frontend contract is unchanged. You can keep re-submitting tags every turn, or stop submitting them on follow-ups and rely on the persisted default. Both work.

### Q11. Honour `503 Retry-After` from `/api/admin/ingest`

Added 2026-04-23 post-incident.

> Late on 2026-04-23 GROBID's request handlers wedged for ~2 hours.
> Two compounding root causes:
>
> 1. **GROBID JVM heap** (default ~4 GB in lfoppiano/grobid:0.8.0)
>    OOM'd in the AsyncAppender thread under sustained concurrent
>    load. Container stayed `Up`, but every PDF parse 503'd
>    silently.
> 2. **`/api/admin/ingest` had no concurrency cap.** Your hook
>    service + cron retry forked **37+ paper_pipeline subprocesses
>    in parallel**, each holding an HTTP connection to GROBID's
>    10-engine pool. The pool stayed permanently saturated. The
>    cron's inner loop kept spinning at ~1 req/s producing 503s
>    without backoff, sustaining the saturation indefinitely.
>
> Two backend fixes shipped same day (already deployed):
>
> - GROBID JVM heap → 12 GB via `JAVA_TOOL_OPTIONS=-Xmx12g -Xms2g`
>   on the grobid service in `docker-compose.yml`. (lfoppiano image
>   ignores `JAVA_OPTS`; only `JAVA_TOOL_OPTIONS` is honoured.)
> - `/api/admin/ingest` now caps at `INGEST_CONCURRENCY=4`
>   concurrent pipelines. Over-cap requests fast-fail in ~5 s with:
>
>   ```
>   HTTP/1.1 503 Service Unavailable
>   Retry-After: 60
>   Content-Type: application/json
>
>   {"detail": {"error": {"message": "Ingest pipeline saturated
>    (>= 4 concurrent jobs). Retry after the cooldown."}}}
>   ```
>
> Watcher daemon's `--workers` reduced to 2 so admin-ingest (4) +
> watcher (2) = 6 of GROBID's 10 engines, leaving headroom.
>
> **What we need on your side**: `hook_service.py` and your
> cron-driven retry sweep need to honour `Retry-After`. Spinning
> at 1 req/s against a 503 endpoint accomplishes nothing and
> recreates the saturation. Reference implementation in
> `scripts/vps/backfill_contributed.py` `post_paper()`, about 8
> lines. Documented in `docs/CONTRIBUTOR-INGEST.md` §"503 +
> Retry-After backpressure".
>
> **Recommended split**:
>
> - `hook_service.py` BackgroundTask: on 503, sleep
>   `Retry-After` seconds → return without moving the file →
>   cron picks it up next pass.
> - Cron-driven retry sweep: on first 503 in the loop, **break
>   out of the loop entirely** rather than continuing through the
>   queue. The next cron tick will succeed once the cluster has
>   spare capacity. Simpler than per-paper sleep, lighter on the
>   cluster.

**Frontend answer:**

> **Both pieces shipped (2026-04-23):**
>
> - **`hook_service.py`**: On 503, logs a warning with the `Retry-After` value, sleeps for that duration (async), then returns without moving the file. The cron picks it up on the next pass.
> - **`backfill_contributed.py`** (cron sweep): `post_paper()` now returns a distinct `HTTP503_SATURATED` status on 503. The main loop checks for this status and breaks out immediately, no further papers attempted. The next cron tick (30 min) retries once the cluster has capacity.
>
> No per-paper sleep in the cron path, clean break on first 503, as recommended.

### QF2. Does `usage` populate correctly for browser chat SSE?

> We observed that browser chat requests via `/api/chat/completions` (persona mode, SSE) DO log non-zero token counts on the gateway side (e.g. florian.taube: 14648, 9560 tokens). But API key requests via `/v1/chat/completions` log 0 tokens. Is the cluster emitting `usage` in persona-mode `done` events but not in raw-mode? Or is the gateway parsing one correctly and not the other?

**Backend answer:**

> **Correct diagnosis, the cluster emits usage for persona-mode but not for raw-mode.** Root cause:
>
> - **Persona path** (`chat_service.stream_chat_completion`) calls vLLM with `stream_options: {"include_usage": true}` (line 479). vLLM then emits a final SSE chunk whose `usage` field is non-empty. chat_service accumulates it and re-emits it in the munin `done` event. Gateway reads non-zero. ✓
> - **Raw-mode path** (`_raw_chat_proxy` in `main.py`) forwards the client's body unchanged and just pipes vLLM's SSE back. External clients (Cursor, aider, OpenAI SDK) don't set `stream_options.include_usage`, they don't care about usage. vLLM obeys and emits no usage chunk. Gateway reads zero.
>
> **Fix shipped with this reply:** the raw-mode proxy now auto-injects `stream_options: {"include_usage": true}` before forwarding. The extra usage chunk is standard OpenAI SSE format; clients either ignore it or log it, both are fine. After redeploy, `/v1/*` API-key requests will also emit `usage` and the gateway will bill correctly. See the commit alongside this doc update.

### QF3. `X-Munin-Ephemeral`: is `ephemeral` body field also supported?

> §1.1 says both `"ephemeral": true` in the request body AND `X-Munin-Ephemeral: true` header are OR'd. The gateway currently only sends the header for `/v1/*`. Should the gateway also set `"ephemeral": true` in the JSON body for belt-and-suspenders, or is the header sufficient?

**Backend answer:**

> **Header alone is sufficient, don't set the body field.** The backend OR's the two signals specifically so the gateway doesn't need to mutate the client's JSON body. Both paths are tested (14/14 unit tests covering both forms pass).
>
> Rationale: touching the body would force the gateway to parse + re-serialise every `/v1/*` request. Today it forwards the body byte-for-byte, which is cheaper and preserves any OpenAI fields we don't explicitly know about (future-proofing). The header is a cheap one-line addition that doesn't interfere with the body.
>
> Only time you'd want both: if some downstream code we haven't written yet inspects the body directly without going through the shared parser. Flag that when it happens.

### QF4. Conversation title for API requests that slip through

> Before the ephemeral fix was deployed, API "ping" test messages created real conversations with title "ping". Now that ephemeral is live, this shouldn't recur. But if a conversation IS created from an API request (e.g., user sends `persona: "chat"` via API intentionally), does the auto-title generator use the first user message? Could we have a fallback like "API conversation" for single-turn API chats?
>
> Current behaviour: first-message truncation is the seed; if the first user message is 60 chars or less, the truncation IS the title verbatim ("ping"). For longer messages, there's an async vLLM call after the first response that generates a 5-8 word title and updates the conversation.

**Backend answer:**

> **Agreed, that's the behaviour, and `"API conversation"` as a default sounds reasonable for the edge case.** Two ways to implement:
>
> 1. **Gateway-side** (preferred, no backend change): if the gateway is stamping `X-Munin-Ephemeral: true` on every `/v1/*` request AND the request body lacks a `persona` field, the conversation will never be created, no title problem. The only path that still creates a conversation from `/v1/*` is a client that *explicitly* sends a persona, which is user intent. In that case "API conversation" as a title is a polite lie, the user asked for a persona flow, they get a titled conversation.
>
> 2. **Backend-side**: if you want a safety net anyway, I can add an `X-Munin-Default-Title` header. Gateway sets it on `/v1/*` → backend uses it when auto-title would otherwise fall back to first-message truncation. Two-line change on each side.
>
> My vote: **option (1) for now**. The ephemeral header already stops 99% of the title pollution. If we see user-persona-via-API calls producing unfortunate titles in practice, we do (2) then. Let me know if you want me to ship (2) proactively instead.
